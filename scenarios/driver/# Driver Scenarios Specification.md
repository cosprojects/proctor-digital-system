# Driver Scenarios Specification

## Назначение

Данный раздел содержит полную спецификацию пользовательских сценариев роли **Driver** (водитель) в системе дистанционной аттестации.

Сценарии являются основой проектирования:

- пользовательских потоков (User Flow);
- Customer Journey Map (CJM);
- экранов интерфейса;
- функциональных элементов;
- компонентной библиотеки;
- бизнес-логики системы.

Все последующие артефакты проекта (Figma, компоненты, API, спецификации, тестовые сценарии) должны опираться именно на данные сценарии.

---

# Основные принципы

При проектировании сценариев используются следующие правила.

## Один сценарий — одна завершенная задача

Каждый сценарий описывает одну логически завершенную пользовательскую цель.

Сценарии не должны пересекаться.

Каждый следующий сценарий начинается ровно в той точке, где завершился предыдущий.

---

## Сценарии описывают поведение системы

Документы не являются описанием экранов.

В сценариях отсутствуют:

- расположение элементов интерфейса;
- дизайн;
- визуальные решения.

Сценарии определяют исключительно:

- поведение пользователя;
- поведение системы;
- реакции на Events;
- ограничения;
- переходы между состояниями.

# Модель прохождения Exam Session

Система работает в модели Asynchronous Proctoring.

Exam Session / Attempt проходят в едином пользовательском сценарии без выбора режима проведения.

Особенности:

- прохождение без предварительной записи;
- автоматический контроль ИИ;
- отложенная проверка;
- отсутствие проктора во время прохождения;
- результат публикуется после проверки.

# Границы ответственности сценариев

## SC-001

Начало аттестации.

Lifecycle State Attempt: **Draft**.

Не содержит подготовки или проверок оборудования.

---

## SC-003

Подготовка пользователя и Environment Checking.

Lifecycle State Attempt: **Environment Checking**.

Проверяются только условия окружения:

- камера;
- интернет;
- освещение;
- положение лица;
- готовность оборудования.

Не содержит:

- Identity Verification;
- загрузку фотографии из КИС АРТ;
- сравнение лица;
- CTA «начать экзамен» или «присоединиться к экзамену».

Переход только в SC-004.

---

## SC-004

Identity Verification и переход Attempt в состояние **Ready**.

Lifecycle States Attempt: **Identity Verification** → **Ready**.

Модель Identity Verification:

- Identity Verification выполняет наша система;
- данные личности и эталонная фотография поступают из КИС АРТ.

Включает:

- загрузку фотографии Driver из КИС АРТ;
- сравнение лица с эталонной фотографией;
- переход Attempt в **Ready** при успешной верификации.

После успешной проверки пользователь получает допуск к Attempt. Экзаменация выполняется в LMS; Attempt — жизненный цикл прокторинга вокруг экзаменации в LMS.

---

## SC-005

Прохождение Attempt в состоянии **In Progress**.

Экзаменация исполняется в LMS. Attempt — жизненный цикл прокторинга вокруг экзаменации в LMS; Attempt не является самим Exam.

Включает:

- отображение хода экзаменации (контент Exam принадлежит LMS);
- мониторинг поведения;
- отображение Alerts (пользовательский интерфейс Observations).

Driver не работает с внутренними сущностями AI напрямую. Внутренний pipeline: Observation → Recommendation → Review → Decision → Publish. Driver видит только Alerts.
AI формирует только Recommendation и не принимает Decision.

---

## SC-006

Завершение Attempt и отображение Lifecycle States:

- **Completed** — Attempt завершена;
- **AI Processing** — анализ Observations и формирование Recommendations;
- **Review Required** — ожидание Review Proctor;
- **Decision Made** — принято Decision (Approved / Rejected / Cancelled / Expired) Proctor или System (только если явно разрешено бизнес-правилами);
- **Published** — Decision опубликован Integration Layer; exam score остаётся во владении LMS; сведения могут быть переданы в КИС АРТ в контексте enrollment;
- **Archived** — Attempt доступна только для просмотра.

Decision не является Lifecycle State.

Appeal вне MVP. После отрицательного Decision доступен только Retake.

# Общие правила проектирования

При проектировании всех сценариев соблюдаются следующие принципы.

- Mobile First.
- Один основной сценарий — один главный экран.
- Максимально автоматизированное взаимодействие.
- Минимум действий пользователя.
- Максимальная прозрачность текущего состояния системы.
- Любая ошибка должна сопровождаться объяснением причины и следующим рекомендуемым действием.
- Пользователь всегда понимает:
  - что сейчас происходит;
  - почему это происходит;
  - что необходимо сделать дальше.

# Lifecycle States Attempt

На протяжении сценариев Driver взаимодействует с Attempt в следующих Lifecycle States (см. EXAM_ATTEMPT_LIFECYCLE.md):

| Lifecycle State | Сценарий Driver |
|-----------------|-----------------|
| Draft | SC-001 |
| Scheduled | — |
| Environment Checking | SC-003 |
| Identity Verification | SC-004 |
| Ready | SC-004 |
| In Progress | SC-005 |
| Completed | SC-006 |
| AI Processing | SC-006 |
| Review Required | SC-006 |
| Decision Made | SC-006 |
| Published | SC-006 |
| Archived | SC-006 |

Переход Draft → Scheduled выполняется системой; пользовательский маршрут начинается с SC-001 (Draft) и продолжается SC-003 (Environment Checking).

Alert — пользовательское отображение Observation, не является Domain Entity.

# Правила развития сценариев

При изменении сценариев запрещается:

- изменять уже утвержденную последовательность без архитектурного решения;
- переносить функциональность между сценариями;
- объединять сценарии;
- дублировать функциональность.

Допускается:

- уточнение Edge Cases;
- детализация Functional Elements;
- уточнение CJM;
- расширение бизнес-правил;
- уточнение системных состояний.
