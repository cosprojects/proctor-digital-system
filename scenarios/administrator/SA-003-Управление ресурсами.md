# SA-003

## 1. Общая информация

- Код сценария: SA-003
- Роль: Administrator
- Название: Управление ресурсами

---

## 2. Цель сценария

Предоставить администратору возможность управлять человеческими ресурсами системы: создавать и вести учётные записи Proctor, контролировать их доступность, рабочую нагрузку, участие в проведении экзаменов и распределение Review Required Attempt.

## 4. Preconditions

- администратор аутентифицирован через SUDIR; Authorization (роли и права) — в нашей системе;
- пользователь обладает правами Administrator;
- ресурсы зарегистрированы в системе.

---

## 5. Trigger

Администратор открывает раздел «Ресурсы».

---

## 6. Основной сценарий

1. Система отображает список ресурсов.
2. По умолчанию отображаются только активные ресурсы.
3. Администратор использует поиск и фильтрацию.
4. Система отображает карточку каждого ресурса.
5. Администратор открывает карточку выбранного ресурса.
6. Система отображает:
   - профиль;
   - роль;
   - текущий статус;
   - текущую загрузку;
   - ближайшие назначенные сессии;
   - историю активности.
7. При необходимости администратор:
   - создаёт учётную запись Proctor (заполнение необходимых данных, назначение роли / Authorization, настройка доступности);
   - изменяет доступность;
   - редактирует профиль;
   - изменяет график;
   - блокирует или активирует ресурс;
   - вручную переназначает Proctor на Exam Session (болезнь, отсутствие, перегрузка);
   - выполняет аварийное перераспределение нагрузки.
8. Система пересчитывает влияние изменений на будущие Exam Session.
9. Если изменения затрагивают активные или запланированные сессии, система показывает последствия до подтверждения.
10. После подтверждения изменения сохраняются и фиксируются в журнале аудита (включая ручное переназначение Proctor).
11. При необходимости администратор управляет распределением Review Required Attempt:
    - видит общее количество завершённых Attempt;
    - количество автоматически обработанных Attempt;
    - количество Attempt в Review Required;
    - количество Attempt, ожидающих Decision;
    - количество завершённых Review;
    - текущую нагрузку каждого Proctor;
    - количество Review Required Attempt, назначенных каждому Proctor;
    - доступность Proctor;
    - потенциальный дефицит ресурсов.
    Конкретный алгоритм распределения не определён.

12. При необходимости администратор изменяет принятое Decision по Attempt:
    - находит Attempt с принятым Decision;
    - изменяет Decision (и при необходимости Conclusion / Comment);
    - система фиксирует изменение в истории с указанием пользователя;
    - изменённое Decision становится актуальным итоговым решением Attempt.

Изменение принятого Decision — административная функция; Proctor принятое Decision не изменяет.

## 7. Альтернативные сценарии

### Ресурс участвует в активной сессии

Изменение ограничивается.

Система объясняет причину ограничения.

---

### Изменение затрагивает будущие сессии

Система показывает список затронутых сессий и предлагает автоматически перераспределить нагрузку.

---

### Недостаточно свободных ресурсов

Система предупреждает о невозможности полного перераспределения.

---

### Ресурс временно недоступен

Статус изменяется автоматически.

Администратор получает рекомендации по дальнейшим действиям.

Типичные причины ручного переназначения Proctor: болезнь, отсутствие, перегрузка. Переназначение фиксируется в audit.

### Proctor Management (Create Proctor)

Административный сценарий создания учётной записи Proctor:

1. Administrator открывает раздел «Прокторы».
2. Выбирает «Создать Proctor».
3. Заполняет необходимые данные (состав полей профиля определяется моделью учётной записи).
4. Назначает роль / Authorization.
5. Настраивает доступность.
6. Сохраняет.
7. Изменение фиксируется в Audit Log.

Существующие административные операции: редактирование, блокировка / деактивация, восстановление, изменение доступности, изменение расписания.

### Decision Change (изменение принятого Decision)

Административная операция изменения принятого Decision по Attempt.

1. Administrator находит Attempt с принятым Decision.
2. Изменяет Decision (и при необходимости Conclusion / Comment).
3. Система фиксирует изменение в истории с указанием пользователя; старое значение не уничтожается.
4. Изменённое Decision становится актуальным итоговым решением Attempt.

Изменение принятого Decision — административная функция; Proctor принятое Decision не изменяет.

## 13. Edge Cases

- изменение активного ресурса;
- двойное редактирование одним и тем же объектом;
- отсутствие свободных ресурсов;
- массовое изменение статусов;
- ошибка перераспределения;
- отмена изменений после расчета последствий;
- недостаточно прокторов для распределения Review Required Attempt;
- изменение распределения во время активной проверки.

---

## 14. Критерии успеха

Сценарий считается завершенным, если:

- администратор получил актуальную информацию о ресурсах;
- влияние изменений рассчитано до их применения;
- изменения безопасно сохранены;
- журнал аудита обновлен;
- система сохранила целостность расписания.
