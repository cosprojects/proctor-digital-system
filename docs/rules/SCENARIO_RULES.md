# SCENARIO_CREATION_RULES.md

# Правила создания сценариев

## Общий принцип

Каждый сценарий является аналитическим артефактом проекта.

Сценарий описывает поведение системы.

Сценарий не является UI-документом.

Сценарий не является пользовательской инструкцией.

---

# Итеративный подход

Сценарии создаются последовательно.

Не изменять ранее утвержденные сценарии без явной задачи.

Не проектировать следующие сценарии до завершения текущего.

После создания сценария сразу создавать соответствующий артефакт в Figma.

---

# Workflow

Для каждого нового сценария необходимо выполнить следующую последовательность.

1.

Провести короткое архитектурное ревью.

Цель ревью:

- выявить слабые места сценария;
- предложить улучшения;
- устранить логические противоречия.

Количество предложений:

не более трех.

После согласования перейти к следующему шагу.

---

2.

Создать Markdown сценарий.

Использовать только утвержденную структуру.

---

3.

Создать визуальный артефакт в Figma.

Использовать существующий шаблон сценария.

Не изменять шаблон.

Создать новый экземпляр.

---

4.

Заполнить артефакт содержимым Markdown.

---

5.

Определить функциональные элементы.

Функциональные элементы должны описывать возможности системы.

Не описывать внешний вид интерфейса.

---

6.

Определить необходимые компоненты.

Сначала использовать существующие компоненты.

Если существующего компонента недостаточно —

только перечислить новый компонент.

Не создавать его.

---

7.

Завершить сценарий.

Сообщить:

- путь к Markdown;
- созданный артефакт Figma;
- выявленные функциональные элементы;
- предлагаемые новые компоненты.

---

# Структура сценария

Каждый сценарий использует следующую структуру.

1. Общая информация

2. Цель сценария

3. JTBD

4. Preconditions

5. Trigger

6. Основной сценарий

7. Альтернативные сценарии

8. CJM

9. User Flow

10. Functional Zones

11. Functional Elements

12. Required Components

13. Edge Cases

14. Success Criteria

15. Next Scenario

Структура является обязательной.

Не изменять порядок разделов.

Не добавлять новые разделы без явной задачи.

---

# Functional Zones

Определять только назначение функциональной зоны.

Не описывать UI.

Не использовать названия компонентов.

---

# Functional Elements

Определять функции системы.

Не описывать дизайн.

Не описывать расположение элементов.

Не описывать визуальное оформление.

---

# Required Components

Не создавать компоненты.

Только определить:

- какие существующие компоненты подходят;

- какие новые компоненты могут понадобиться.

Создание компонентов выполняется отдельной задачей.

---

# Figma

Для каждого сценария обязательно создать отдельный экземпляр шаблона.

Использовать только существующий шаблон.

Не изменять шаблон.

Размещать сценарии последовательно.

---

# Правило проекта

После создания сценария не выполнять его улучшение.

Сразу переходить к следующему сценарию.

Возврат к сценарию выполняется только после завершения всей группы сценариев роли.

Сначала Driver.

Затем Proctor.

Затем Administrator.

Затем AI.

Только после этого начинается проектирование функциональных элементов и компонентов.
