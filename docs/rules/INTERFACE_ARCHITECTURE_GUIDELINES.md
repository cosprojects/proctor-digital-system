# Interface Architecture Guidelines

Версия: 1.0

---

# Цель

Настоящий документ определяет единые правила построения интерфейсов цифровой системы прокторинга и аттестации.

Все экраны проекта должны проектироваться на основе данных принципов.

Документ является обязательным для всех последующих сценариев, компонентов и экранов.

---

# Основной принцип

Интерфейс является рабочим инструментом.

Его задача — максимально быстро помочь пользователю выполнить действие.

Интерфейс не должен демонстрировать возможности системы.

Интерфейс должен помогать выполнять задачу.

---

# Design Philosophy

При проектировании придерживаться следующих принципов.

- Functional First
- Content First
- Accessibility First
- Enterprise UX
- Progressive Disclosure
- Consistency
- Minimal Cognitive Load
- High Information Density (где необходимо)
- Mobile First для водителя
- Desktop First для проктора и администратора

---

# Основные принципы

## Один экран — одна основная задача

Каждый экран должен иметь одну главную цель.

Дополнительные действия являются вторичными.

---

## Один главный CTA

На каждом экране должен присутствовать только один Primary Action.

Все остальные действия имеют меньший визуальный приоритет.

---

## Очевидная иерархия

Каждый экран должен отвечать на три вопроса.

Что происходит?

Что нужно сделать?

Что произойдет дальше?

---

## Минимум когнитивной нагрузки

Не перегружать пользователя.

Показывать только ту информацию, которая необходима в текущий момент.

---

## Прогрессивное раскрытие информации

Сложная информация появляется только тогда, когда она действительно нужна.

---

# Информационная архитектура

Каждый экран состоит из логических блоков.

```
Заголовок

↓

Основное действие

↓

Контент

↓

Дополнительная информация

↓

Вторичные действия
```

---

# Навигация

Навигация должна быть постоянной и предсказуемой.

Использовать одинаковые принципы на протяжении всей системы.

---

## Driver

Навигация максимально упрощена.

Не более одного уровня вложенности.

Основной сценарий должен проходиться последовательно.

---

## Proctor

Допускается использование постоянной боковой навигации (Sidebar).

Навигация должна обеспечивать быстрый доступ к:

- Сессиям
- Участникам
- Нарушениям
- Отчетам

---

## Administrator

Использовать постоянную Sidebar Navigation.

Навигация должна быть ориентирована на работу с большим количеством разделов.

---

# Sidebar

Sidebar используется только там, где она действительно повышает эффективность.

Sidebar должна содержать только разделы верхнего уровня.

Не использовать вложенность более двух уровней.

---

# Layout

Использовать Auto Layout.

Все интерфейсы строятся на единой сетке.

Использовать только переменные проекта.

---

# Карточки

Карточка является основной единицей интерфейса.

Каждая карточка должна содержать:

- заголовок;
- содержимое;
- действия.

Карточка не должна содержать несколько независимых сценариев.

---

# Формы

Формы должны быть максимально короткими.

Использовать группировку полей.

Обязательные поля должны быть очевидны.

---

# Таблицы

Использовать таблицы только там, где требуется сравнение большого количества объектов.

Во всех остальных случаях использовать карточки.

---

# Видео

Видео является основным объектом системы.

Видео должно иметь приоритет над вторичной информацией.

Все элементы управления видео должны быть унифицированы.

---

# Видеоконференции

Интерфейсы видеоконференций должны придерживаться следующих принципов.

- Максимальная площадь видеопотока.
- Минимальное количество перекрывающих элементов.
- Панели появляются только при необходимости.
- Управление находится в привычных местах.
- Критические события отображаются мгновенно.

---

# Мониторинг

Информация о нарушениях должна отображаться визуально.

Использовать:

- цвет;
- статус;
- индикатор;
- бейдж;

не использовать длинные текстовые сообщения.

---

# Статусы

Все статусы должны иметь одинаковую структуру.

Статус состоит из:

- цвета;
- иконки;
- короткого текста.

---

# AI

ИИ является частью интерфейса.

Рекомендации ИИ отображаются как отдельный информационный блок.

ИИ никогда не принимает окончательное решение без явного отображения результата пользователю или проктору.

---

# Уведомления

Использовать три уровня уведомлений.

Информационное.

Предупреждение.

Критическое.

---

# Ошибки

Ошибки должны объяснять:

что произошло;

почему произошло;

что делать дальше.

---

# Компоненты

Все экраны собираются исключительно из компонентов библиотеки.

Запрещается создавать локальные элементы.

---

# Переменные

Все визуальные свойства используют только Variables проекта.

Запрещается использовать локальные значения цветов, размеров, отступов и типографики.

---

# Адаптивность

Все новые компоненты должны поддерживать:

Desktop

Tablet

Mobile

---

# Доступность

При проектировании соблюдать WCAG.

Использовать достаточную контрастность.

Не использовать цвет как единственный способ передачи информации.

---

# Производительность

Интерфейс должен оставаться читаемым при:

30–40 видеопотоках;

большом количестве карточек;

таблицах;

аналитике.

---

# Итоговый принцип

Каждый новый экран должен отвечать следующим критериям.

- Решает одну задачу.
- Использует существующие компоненты.
- Использует существующие переменные.
- Соблюдает единый Layout.
- Соответствует правилам системы.
- Может быть использован повторно в других сценариях.
