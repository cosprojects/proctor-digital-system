# UX Interaction Principles

## Назначение

Документ определяет принципы проектирования пользовательского взаимодействия в Proctor Digital System.

Все пользовательские сценарии, UX-паттерны, компоненты, экраны и новые функциональные возможности должны соответствовать данным принципам.

При возникновении противоречий между локальным UX-решением и данным документом приоритет всегда имеют принципы, описанные здесь.

---

# Основные принципы

## 1. Интерфейс обслуживает процесс, а не наоборот

Интерфейс существует для поддержки бизнес-процесса.

Каждый экран должен помогать пользователю выполнять задачу, а не демонстрировать функциональность системы.

---

## 2. Интерфейс строится вокруг рабочей единицы

Пользователь всегда работает с конкретной рабочей единицей (Work Unit).

Рабочая единица определяет:

- контекст;
- состояние;
- доступные действия;
- связанные объекты;
- историю изменений.

Примеры:

Driver → Attempt

Proctor → Attempt (Session — пользовательский объект верхнего уровня)

Administrator → Exam Session / Resource / Configuration

Экран строится вокруг Work Unit, а не вокруг структуры меню.

Для роли Proctor:

- Attempt — основная единица работы проктора (Session — пользовательский объект верхнего уровня);
- UI-представление «Требуют проверки» — фильтр общего потока Attempt, а не отдельная сущность;
- модель Review Batch не используется; распределение Review Required Attempt — административная функция.

---

## 3. Контекст определяет интерфейс

Перед выполнением любого действия пользователь должен понимать:

- с чем он работает;
- текущее состояние объекта;
- последствия возможных действий.

Контекст всегда отображается раньше доступных действий.

---

## 4. Один экран — одна доминирующая задача

Каждый экран имеет одну основную цель.

Дополнительные действия допускаются только тогда, когда они непосредственно поддерживают выполнение основной задачи.

---

## 5. Пользователь принимает только необходимые решения

Все решения, которые могут быть приняты автоматически без потери качества процесса, должны приниматься системой.

Пользователь подключается только в случаях, когда требуется экспертная оценка или подтверждение.

---

## 6. AI рекомендует, человек утверждает

AI никогда не принимает окончательное решение, если это не разрешено бизнес-правилами.

Интерфейс обязан разделять:

- Observation;
- Recommendation;
- Decision.

Эти сущности никогда не смешиваются визуально или логически.

---

## 7. Управление вниманием важнее количества информации

Интерфейс показывает только информацию, необходимую в текущем контексте.

Пользователь не должен конкурировать с интерфейсом за внимание.

---

## 8. Приоритет важнее времени возникновения

Информация сортируется по степени важности.

Критические события всегда отображаются выше информационных независимо от времени появления.

---

## 9. Интерфейс масштабируется без изменения модели

Рост количества данных не должен менять модель взаимодействия.

При увеличении объёма информации используются:

- группировка;
- агрегация;
- фильтрация;
- приоритизация.

Пользователь работает с одинаковой моделью независимо от количества объектов.

---

## 10. Массовые действия предпочтительнее повторяющихся одиночных

Если пользователь регулярно выполняет одинаковые действия, система должна предоставлять возможность пакетной обработки.

Массовые операции являются предпочтительным способом работы.

---

## 11. Решение принимается максимально близко к контексту

Пользователь не должен покидать рабочее пространство для выполнения действия.

Все решения принимаются непосредственно рядом с объектом, к которому относятся.

---

## 12. Одна Domain Entity — одна модель взаимодействия

Каждая Domain Entity использует единую модель взаимодействия независимо от роли пользователя.

Визуальное представление может отличаться.

Способы работы, состояния и действия остаются едиными.

---

## 13. Интерфейс раскрывается постепенно

Пользователь сначала видит только необходимый минимум информации.

Дополнительные сведения раскрываются по мере необходимости.

---

## 14. Действия важнее навигации

Пользователь должен думать о выполнении задачи, а не о перемещении между разделами.

Навигация должна быть следствием процесса, а не самостоятельной задачей.

---

## 15. Состояние важнее оформления

Каждый объект обязан явно отображать своё состояние.

Изменение состояния всегда важнее визуального оформления.

---

## 16. Ошибки должны восстанавливаться

Каждая ошибка должна сопровождаться понятным способом восстановления.

Интерфейс никогда не должен оставлять пользователя в тупике.

---

## 17. Интерфейс деградирует, а не прекращает работу

При отказе внешних сервисов система сохраняет максимально возможную функциональность.

Недоступные возможности явно обозначаются.

---

## 18. Все изменения обратимы до публикации результата

Любое действие может быть изменено до момента публикации результата, если это допускается бизнес-правилами.

---

## 19. Интерфейс объясняет последствия действий

Перед выполнением критического действия пользователь должен понимать:

- что произойдёт;
- какие объекты будут затронуты;
- можно ли отменить действие.

---

## 20. История важнее памяти пользователя

Интерфейс должен предоставлять необходимый контекст:

- историю изменений;
- предыдущие решения;
- изменение состояний;
- связанные объекты.

Пользователь не должен помнить эти данные самостоятельно.

---

## 21. Все роли используют единую UX-модель

Driver, Proctor и Administrator используют разные сценарии, но единые принципы взаимодействия.

Новые роли не должны создавать новую UX-модель без объективной необходимости.

---

## 22. Автоматизация развивается постепенно

Автоматизация должна повышаться по мере накопления доверия к алгоритмам.

Типовая последовательность:

Observation

↓

Recommendation

↓

Bulk Action

↓

Auto Decision (если допускается бизнес-правилами)

Полностью автоматические решения допускаются только для заранее определённых процессов.

---

## 23. Сначала существующий паттерн, потом новый

При реализации новой функциональности необходимо в первую очередь использовать существующие UX-паттерны и компоненты.

Создание нового паттерна допускается только после подтверждения невозможности переиспользования существующих решений.

---

# Принципы композиции экранов

Любой экран строится по единой модели.

Work Unit

↓

Context

↓

Current State

↓

Primary Action

↓

Secondary Actions

↓

Related Information

↓

History

---

# Принципы проектирования компонентов

Каждый компонент отвечает только за одну задачу.

Компонент не содержит бизнес-логику.

Компоненты переиспользуются между ролями.

Компоненты независимы от конкретного сценария.

Компоненты работают с Domain Entity, а не со сценариями.

---

# Принципы развития системы

При добавлении новой функциональности необходимо:

- использовать существующую Domain Entity;
- использовать существующий UX-паттерн;
- использовать существующие компоненты;
- использовать существующую терминологию;
- использовать существующие состояния жизненного цикла.

Любое отклонение должно быть архитектурно обосновано.

---

## Mobile First для Driver

Интерфейсы роли Driver проектируются по принципу Mobile First.

Основной сценарий использования предполагает прохождение экзамена с мобильного устройства.

При проектировании необходимо исходить из следующих предположений:

- основное устройство — смартфон;
- управление осуществляется одной рукой;
- возможны нестабильное соединение и смена ориентации экрана;
- все критически важные действия должны быть доступны без горизонтальной прокрутки;
- все обязательные элементы должны помещаться в безопасной области экрана мобильного устройства.

Desktop-версия Driver является адаптацией мобильного сценария.

---

Интерфейсы ролей Proctor и Administrator проектируются по принципу Desktop First.

Основное устройство:

- ноутбук;
- настольный компьютер;
- широкоформатный монитор.

Mobile-версия для данных ролей не является целевым сценарием и рассматривается только как вспомогательная.

# Что не определяет данный документ

Документ не определяет:

- пользовательские сценарии;
- структуру экранов;
- визуальный стиль;
- дизайн-систему;
- компонентную библиотеку;
- бизнес-логику;
- архитектуру API;
- модель данных.

Документ определяет исключительно принципы пользовательского взаимодействия.
